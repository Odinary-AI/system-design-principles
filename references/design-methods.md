# 设计分析方法

方法用于形成和检验证据，不是每项任务都必须执行的流程。按当前问题选择相关部分，复用已有需求、设计和观察；最小结果可直接在对话中表达，不要求新增矩阵、模型、报告或治理角色。原则编号见 [原则与诊断参考](principles.md)。

| 当前问题 | 选用方法 |
|---|---|
| 过早绑定技术、能力或职责遗漏 | 需求—功能—实现映射 |
| 要求来源、覆盖或改动影响不明 | 需求与证据追踪 |
| 时序、积累、反馈或整体行为异常 | 状态、流与反馈分析 |
| 局部达标而整体可能超限 | 预算与边界分析 |
| 方案优劣取决于关键假设 | 方案取舍与敏感性分析 |
| 故障传播或危险控制不明 | 故障与危险分析 |
| 模型、测试或旧版本证据能否支持当前声明 | 分层验证与变更影响检查 |

## 需求—功能—实现映射

- 使用条件：需设计或比较实现，已有技术选择可能掩盖实际能力要求（P01、P02、P04）。
- 所需信息：真实任务、成功标准、硬约束和可用的技术、设备、人员及外部依赖。
- 最小做法：区分“需要什么能力”与“由什么实现”；将关键能力分配到责任主体，说明输入输出和关系；结合实现可行性反向修正分配，检查遗漏与冲突。按变化与失效关系确定模块边界，不直接把流程步骤当作模块。
- 支持判断：能力是否覆盖、职责是否适当、实现选择是否有依据；输出足以比较的能力—职责—实现关系。
- 边界：现有设备或指定技术可以是硬约束；功能与实现之间允许反复推导，不要求先完成全套功能模型，也不要求功能与零件一一对应。

## 需求与证据追踪

- 使用条件：关键要求的来源、责任、验收或变更影响不清楚（P01、P02、P07、P11）。
- 所需信息：有效需要和约束、设计决定、相关实现及验证证据。
- 最小做法：正向连接需要、功能/约束、设计责任和验收证据；反向核对机制和测试服务什么要求。区分外部要求、由设计推导的要求及暂定假设；对推导要求说明依据，检查上层要求是否由下层共同覆盖。
- 支持判断：识别遗漏、无依据功能和受影响证据；短小对应关系或已有文档链接即可。
- 边界：旧实现不自动成为需求，没有直接上层文字也不自动证明某要求多余。仅追踪会改变当前判断的范围，不强制全量矩阵。

## 状态、流与反馈分析

- 使用条件：整体异常可能由状态、时序、积累或反馈产生（P02、P05、P08、P09、P16）。
- 所需信息：代表性场景、状态和变化条件、物料/能量/信息流、处理与观测时间、相关观测。
- 最小做法：沿相关路径检查流入、流出、积累及上下限；找出信息如何影响动作、动作如何改变被观察状态，核对延迟、响应速度与控制归属；检查启动、切换、扰动及恢复中会改变判断的状态。用时序证据或小实验区分反馈解释与其他根因。
- 支持判断：说明导致整体行为的具体机制、关键边界和可检验的改进位置；可用短文、时序图或简单模型。
- 边界：并非所有反馈都有害，也不是所有异常都有反馈根因；不从反复波动直接断定控制参数错误，不凭相关性确认因果。具体增益、周期和稳定性结论需要对应模型或测量，不能任意指定。

## 预算与边界分析

- 使用条件：时间、质量、功率、热量、内存、带宽、精度或人员处理能力可能决定可行性（P05、P09、P12、P14）。
- 所需信息：整体限制、单位、运行场景、各部分需求/分配、共享关系及波动或误差依据。
- 最小做法：按实际关系汇总串行路径、并发需求、互斥状态和共享竞争，核对峰值、持续负载及恢复阶段；精度预算检查误差传播与相关性。记录整体限制、分配依据、组合方式和余量，变更后核对受影响项。
- 支持判断：整体是否可行、瓶颈在哪里、何种条件耗尽余量，以及最小调整能否改善目标。
- 边界：互斥需求不能机械相加，依赖关系未经证明也不能按完全独立组合误差。区分估算与实测，不从平均值推断峰值或尾部表现；不设统一余量比例或引入未经核对的公式库。

## 方案取舍与敏感性分析

- 使用条件：存在实质可行选择，或推荐依赖不确定的负载、成本、环境等假设（P03、P07、P11、P14）。
- 所需信息：共同场景、硬约束、质量优先级、候选方案及关键假设的有依据范围。
- 最小做法：先排除违反硬约束的方案，再在相同任务和生命周期边界下比较收益、代价、依赖及风险；包含合理的维持现状或最小修改。检查关键假设变化是否改变选择，确定推荐成立条件和优先补证项。
- 支持判断：推荐方案、成立条件，以及什么新证据会改变推荐；方法服务于 [主流程的设计判断](../SKILL.md#设计)。
- 边界：没有可靠范围时指出缺口，不虚设扰动幅度、概率或评分权重。区分实际随机波动与知识不足，分别考虑容错措施和补充信息。只有进一步调查可能改变判断或降低重要风险，且收益与成本相称时才追加；不要求消除所有不确定性。

## 故障与危险分析

- 使用条件：失败后果、传播或危险控制会改变设计与验收（P08、P09、P10、P16）。
- 所需信息：任务边界、不可接受后果、相关状态/接口/控制动作、故障模型和既有保护。
- 最小做法：按问题选择分析视角：失效模式与影响分析检查部件如何失效及其后果；故障树从某种整体失败追踪条件组合；系统控制约束分析检查动作缺失、错误动作、错误时机/顺序或持续时间如何导致危险。沿相关路径检查共因依赖、控制与反馈、人机交接和恢复，再明确措施及支持它们的证据。
- 支持判断：具体失效或危险场景、需要保持的约束、控制措施和验证方式；允许以一个相关场景完成局部分析。
- 边界：可组合方法但不默认全部执行；可靠性不能代替安全，正常部件的交互也可能造成危险。只有安全后果需要时才开展专业分析；缺少概率资料不编造风险数值，普通走查不构成安全认证。涉及真实安全关键实施时需相应领域依据。

## 分层验证与变更影响检查

- 使用条件：需支持重要声明，或模型、对象、版本、环境及假设变化可能使证据失效（P07、P11、P15）。
- 所需信息：待判断的要求与声明、证据对象和条件、模型假设、当前版本及变更范围。
- 最小做法：区分符合规格的验证与满足实际需要的确认；部件检查、集成检查和真实任务证据分别支持对应层次。模型先核对推导/实现是否正确，再检查它在使用范围内能否描述现实，记录校核依据与忽略因素。将关键证据关联到对象、版本、环境和假设，变更后只重查受影响或已失效的证据。
- 支持判断：当前声明的证据范围、尚缺的最小检查，以及变更后仍可复用或需重做的验证。
- 边界：仿真或模型内部自洽不能直接证明实际系统有效；稳态证据不自动覆盖启动、切换和瞬态。仅有设计材料时不能声称行为已验证。迁移含义、共存及恢复问题读取 [迁移设计方法](migration-design.md)，不在这里另建迁移流程。

原始来源与适用限制见 [案例与原始来源](cases-and-sources.md#通用原则与方法的补充来源)。来源解释机制，不替代当前任务证据。
